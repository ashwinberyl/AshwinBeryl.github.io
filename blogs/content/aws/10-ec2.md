# A Server With No Open Door 🖥️

An EC2 instance is the most familiar thing in AWS: a virtual machine. It's also where the old habits cause the most damage. Open port 22 to the world. Copy a key pair around. Paste access keys into `~/.aws/credentials`.

On the platform we do none of that. The instance sits in a **private subnet** with **no inbound ports at all**. We reach it through **Session Manager**. It gets its permissions from an **IAM role**. And every credential it uses is short-lived and delivered by the platform itself.

This is also our first chance to use the Linux skills from Post 09 on something real.

---

## What You Launch 🚀

| Piece | What it is |
|---|---|
| **AMI** | The template: an OS image, a snapshot of a root volume. **Region-specific** |
| **Instance type** | CPU, memory and network sizing. `t3.micro` = family `t`, generation 3, size `micro`. A `g` in the name (`m7g`) means **Graviton (arm64)** |
| **EBS volume** | A network-attached block disk. Lives in **one AZ**. The root volume is EBS |
| **Instance store** | Disk physically attached to the host. **Fast, and lost** on stop or terminate |
| **ENI** | The network interface: private IP, security groups, optionally a public IP |
| **Instance profile** | The wrapper that attaches an **IAM role** to an instance |
| **User data** | A script cloud-init runs **on first boot** |
| **Key pair** | An SSH key. We won't use one |

### Instance lifecycle

| State | Compute billed? | EBS billed? | Notes |
|---|---|---|---|
| **running** | Yes | Yes | |
| **stopped** | **No** | **Yes** | Private IP kept. Public IP **released**. Instance store **lost** |
| **terminated** | No | Only volumes without *delete on termination* | **Irreversible** |

## Getting In: Session Manager 🔌

**AWS Systems Manager Session Manager** gives you a shell through an HTTPS connection that the **instance itself opens outward**. Nothing connects in.

For it to work, three things must be true:

1. **The SSM Agent is running** (preinstalled on Amazon Linux 2023).
2. **The instance has a role** that allows SSM (`AmazonSSMManagedInstanceCore`).
3. **The instance can reach** the `ssm`, `ssmmessages` and `ec2messages` endpoints, through a **NAT gateway** or three **interface endpoints**.

Benefits over SSH: no inbound port, no key pair to distribute, access controlled by **IAM**, and every session can be **logged** to CloudWatch Logs or S3. You land as `ssm-user`.

## The Instance Metadata Service 🪪

Inside every instance, the address `169.254.169.254` serves information about the instance, including the **temporary credentials for its role**. That's how code on the instance calls AWS with no keys configured: the SDK fetches credentials from there and refreshes them.

There are two versions:

| | **IMDSv1** | **IMDSv2** |
|---|---|---|
| Method | Plain `GET` | **PUT for a session token first**, then `GET` with a header |
| Risk | A server-side request forgery (SSRF) bug in an app can steal the role credentials | Much harder to abuse |
| Today | Avoid. **Require v2** on every instance | The default on current AMIs |

The **hop limit** (default 1 in many setups, 2 on some) decides whether a container on the instance can reach the service.

## Nuances & Misconceptions 🧩

| What people assume | What's actually true |
|---|---|
| "A stopped instance is free." | Compute stops billing, but **EBS volumes and any Elastic IP still bill**, and you lose the public IP and any instance store data. |
| "Stop and terminate are almost the same." | **Terminate is permanent.** The instance is gone, and so is any volume marked *delete on termination* (the root volume by default). |
| "I need an SSH key to manage the machine." | **Session Manager** needs no key and no open port. A key pair can only be chosen **at launch**, so "no key" is a decision, not an oversight. |
| "The instance profile *is* the role." | It's a **container for one role**. The console hides it by creating one with the same name. The CLI and CloudFormation make you create both. |
| "IMDSv1 is fine, it's internal." | Any SSRF flaw in an app on the host can read role credentials from it. **Require IMDSv2.** |
| "User data runs at every boot." | It runs **once**, at first boot, as **root** (limit 16 KB). Errors appear in `/var/log/cloud-init-output.log`, not in the console. |
| "`t3.micro` is cheap so it's safe." | T3 instances default to **unlimited** burst mode. Sustained CPU use can add a **surplus-credit charge**. Watch `CPUCreditBalance`. |
| "My volume is in the region, so I can attach it anywhere." | EBS volumes are **AZ-scoped**. To move one, **snapshot** it and create a new volume in the target AZ. |
| "An AMI ID works in every region." | AMI IDs are **per region**. Look the current one up through the public SSM parameter `/aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64`. |
| "I attached `/dev/sdf`, so I'll see `/dev/sdf`." | On current instance types it appears as **`/dev/nvme1n1`**. Use `lsblk` and **UUIDs**. |
| "Encrypting the root volume with a custom key is only a checkbox." | The instance now **depends on that key**. Disable or delete it and the instance **can't start**. |
| "Session Manager works the moment I launch." | It needs the **agent, the role and a network path**. A wait of a minute or two for *SSM ping: Online* is normal, and a missing path shows as *Offline* forever. |
| "I can't change an instance's size." | You can: **stop**, change the instance type, **start**. (Stay within the same CPU architecture.) |

## Lab: Launch a Private Instance and Use It 🛠️

Sign in as Jim in **N. Virginia**. Make sure the NAT gateway is running (Post 04).

### 1. Create the role

1. **IAM, Roles, Create role.** Trusted entity **AWS service**, use case **EC2**.
2. Attach the managed policy **`AmazonSSMManagedInstanceCore`**.
3. Name it **`plat-ec2-role`** and create it. The console also creates an **instance profile** with the same name.
4. Open the role, **Add permissions, Create inline policy, JSON**. Paste this, replacing the account ID, the file system ID, and the access point ID with yours (find the last two in the EFS console):

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadPlatData",
      "Effect": "Allow",
      "Action": ["s3:ListBucket", "s3:GetObject"],
      "Resource": [
        "arn:aws:s3:::plat-data-123456789012-us-east-1",
        "arn:aws:s3:::plat-data-123456789012-us-east-1/*"
      ]
    },
    {
      "Sid": "UsePlatKeyViaS3",
      "Effect": "Allow",
      "Action": ["kms:Decrypt"],
      "Resource": "arn:aws:kms:us-east-1:123456789012:key/<your-key-id>",
      "Condition": { "StringEquals": { "kms:ViaService": "s3.us-east-1.amazonaws.com" } }
    },
    {
      "Sid": "MountPlatEfs",
      "Effect": "Allow",
      "Action": ["elasticfilesystem:ClientMount", "elasticfilesystem:ClientWrite"],
      "Resource": "arn:aws:elasticfilesystem:us-east-1:123456789012:file-system/fs-0123456789abcdef0",
      "Condition": {
        "StringEquals": {
          "elasticfilesystem:AccessPointArn": "arn:aws:elasticfilesystem:us-east-1:123456789012:access-point/fsap-0123456789abcdef0"
        }
      }
    }
  ]
}
```

Name it `plat-ec2-data-access`. This is **least privilege in practice**: one bucket, one key (and only through S3), one file system through one access point.

### 2. Launch the instance

**EC2, Launch instance**:

| Setting | Value |
|---|---|
| Name and tags | `plat-ec2`, tag `project = plat` (apply to instances and volumes) |
| AMI | **Amazon Linux 2023** (64-bit x86) |
| Instance type | **t3.micro** (or the free-tier-eligible type shown) |
| Key pair | **Proceed without a key pair** |
| VPC and subnet | `plat-vpc`, **`plat-private-a`** |
| Auto-assign public IP | **Disable** |
| Security group | **Select existing: `plat-app-sg`** |
| Root volume | **8 GiB gp3**, **Encrypted**, KMS key **`plat-data`** |
| Second volume | **Add new volume**: `/dev/sdf`, **5 GiB gp3**, **Encrypted**, key **`plat-data`** |
| IAM instance profile | **`plat-ec2-role`** |
| Metadata version | **V2 only (token required)** |

Under **Advanced details, User data**, paste:

```bash
#!/bin/bash
dnf install -y amazon-efs-utils
mkdir -p /mnt/efs
echo "user-data ran at $(date -u)" > /var/log/plat-userdata.txt
```

Launch it. Notice that **no inbound rule exists anywhere**: `plat-app-sg` has none.

### 3. Connect with Session Manager

1. **EC2, Instances**, select `plat-ec2`, **Connect, Session Manager, Connect**. If the button is greyed out, wait a couple of minutes for the agent to register (check **Systems Manager, Fleet Manager** for the instance showing *Online*).

```bash
whoami
cat /etc/os-release | head -2
cat /var/log/plat-userdata.txt
```

```text
ssm-user
NAME="Amazon Linux"
VERSION="2023"
user-data ran at Sun Nov  8 10:20:11 UTC 2026
```

### 4. See the identity, and the metadata service

```bash
aws sts get-caller-identity
```

```json
{
    "UserId": "AROAEXAMPLEEXAMPLE:i-0abc123def4567890",
    "Account": "123456789012",
    "Arn": "arn:aws:sts::123456789012:assumed-role/plat-ec2-role/i-0abc123def4567890"
}
```

No keys are configured anywhere on this machine. Now see where the credentials come from:

```bash
curl -s -o /dev/null -w "v1 style, no token: %{http_code}\n" http://169.254.169.254/latest/meta-data/

TOKEN=$(curl -s -X PUT http://169.254.169.254/latest/api/token \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 300")
curl -s -H "X-aws-ec2-metadata-token: $TOKEN" http://169.254.169.254/latest/meta-data/instance-id; echo
curl -s -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/iam/security-credentials/; echo
```

```text
v1 style, no token: 401
i-0abc123def4567890
plat-ec2-role
```

Without a token you get **401**. That's IMDSv2 doing its job.

### 5. Practise Linux on a real host

```bash
systemctl status amazon-ssm-agent --no-pager | head -4
sudo journalctl -u amazon-ssm-agent --no-pager | tail -3
sudo tail -5 /var/log/cloud-init-output.log
df -h /
lsblk
```

`lsblk` shows `nvme0n1` (the 8 GB root, with partitions) and `nvme1n1` (the 5 GB disk, **no partition, no mount point**, even though you asked for `/dev/sdf`). Put the disk to work:

```bash
sudo mkfs.xfs /dev/nvme1n1
sudo mkdir /data
sudo mount /dev/nvme1n1 /data
sudo blkid /dev/nvme1n1
```

Copy the `UUID=...` value and add it to `fstab`, with `nofail`:

```bash
echo "UUID=<paste-uuid-here>  /data  xfs  defaults,nofail  0  2" | sudo tee -a /etc/fstab

sudo umount /data
sudo mount -a          # reads /etc/fstab: proves the entry is correct before a reboot does
df -h /data
```

```text
Filesystem      Size  Used Avail Use% Mounted on
/dev/nvme1n1    5.0G   68M  4.9G   2% /data
```

Always test an `fstab` change with `mount -a` **before** you reboot. A wrong entry without `nofail` can leave the instance unreachable.

### 6. Mount EFS over TLS, with IAM

Use your own file system and access point IDs:

```bash
sudo mount -t efs -o tls,iam,accesspoint=fsap-0123456789abcdef0 fs-0123456789abcdef0:/ /mnt/efs

df -h /mnt/efs
echo "hello from plat-ec2" | sudo tee /mnt/efs/hello.txt
ls -ln /mnt/efs
```

```text
-rw-r--r-- 1 1000 1000 20 Nov  8 10:31 hello.txt
```

You wrote as root (`sudo`), yet the file belongs to **UID 1000, GID 1000**. That's the **access point** from Post 07 enforcing its POSIX identity. Three layers made this succeed: a route to the mount target, `plat-efs-sg` allowing `plat-app-sg` on 2049, and the role's `ClientMount` permission. Make it permanent:

```bash
echo "fs-0123456789abcdef0:/ /mnt/efs efs _netdev,tls,iam,accesspoint=fsap-0123456789abcdef0 0 0" \
  | sudo tee -a /etc/fstab
sudo umount /mnt/efs && sudo mount -a && ls /mnt/efs
```

### 7. Use S3 through the role

```bash
BUCKET=plat-data-123456789012-us-east-1
aws s3 ls s3://$BUCKET/raw/
aws s3 cp s3://$BUCKET/raw/events.csv - | head -2
```

```text
2026-11-08 09:40:11    ...    events.csv
event_id,user_id,plan,sessions_7d,minutes_7d,tickets_30d,churned
e00001,u1042,free,...
```

It works because the role allows `s3:GetObject` **and** `kms:Decrypt` through S3. Remove the second statement and you'd meet the Post 06 error again.

### 8. See what stop does

From the console, **Instance state, Stop instance**. Open the instance: the **private IP is unchanged** when you start it again (private IPs survive stop and start; public IPs don't). Start it again, and re-run `df -h` to confirm `/data` and `/mnt/efs` mounted themselves from `fstab`.

| Keep | Pause or delete |
|---|---|

## Quick Quiz 🧠

**Q1.** You stop an instance overnight. Which charges continue?

<details>
<summary>Show answer</summary>

**EBS volumes** (root and data) and any **Elastic IP** keep billing. Compute charges stop. You also lose the instance's public IP and anything on instance store volumes.

</details>

**Q2.** Session Manager shows the instance as *Offline* in Fleet Manager. Name the three prerequisites to check.

<details>
<summary>Show answer</summary>

(1) the **SSM Agent** is installed and running, (2) the instance has a **role with `AmazonSSMManagedInstanceCore`** (via an instance profile), (3) there's a **network path** to the `ssm`, `ssmmessages` and `ec2messages` endpoints, through NAT or interface endpoints.

</details>

**Q3.** An application on the instance has an SSRF bug. Why does requiring IMDSv2 reduce the risk?

<details>
<summary>Show answer</summary>

IMDSv2 requires a **PUT request to obtain a session token**, then a header on later requests. A typical SSRF bug lets an attacker trigger only simple GET requests, so it can't complete the handshake and can't read the role credentials.

</details>

**Q4.** You added a data disk to `fstab` using `/dev/nvme1n1` and no `nofail`. After a stop and start the instance doesn't come up. Why, and what should you have done?

<details>
<summary>Show answer</summary>

Device names and ordering can change, and with no `nofail` a missing or renamed device **blocks boot**. Reference the disk by **UUID**, add **`nofail`**, and test with `sudo mount -a` before rebooting.

</details>

**Q5.** The EFS mount works for the role in step 6. Name the three layers that all had to allow it.

<details>
<summary>Show answer</summary>

**Network:** a route to the mount target, and `plat-efs-sg` allowing the client's security group on TCP 2049. **IAM:** the role allows `elasticfilesystem:ClientMount` (and `ClientWrite`) on the file system through that access point. **EFS configuration:** the file system policy permits the connection (it enforces TLS, which the mount used) and the access point maps the POSIX identity.

</details>
