# The Bucket Everything Reads From 🪣

S3 is the most used service on AWS, and almost every other post in this series touches it: Lambda reads uploads from it, containers list it, SageMaker trains from it, and pipelines store artifacts in it.

It's also where a lot of production incidents begin, usually in one of two ways. Someone makes data **too public**, or someone makes it **unreadable** by the very role that needs it.

Here we build the **platform's data lake bucket** the way you'd want it in production: private, encrypted with our own key, versioned, and tiered to cheaper storage as data ages.

---

## What S3 Is (and Isn't) 📦

S3 is an **object store**, not a file system.

| Term | Meaning |
|---|---|
| **Bucket** | A container with a **globally unique name**, living in one region |
| **Object** | Data (up to 5 TB) plus metadata, identified by a **key** |
| **Key** | The full name: `raw/2026/events.csv` |
| **Prefix** | The part of a key up to a delimiter. It looks like a folder, but it's just a string |
| **Version ID** | A unique ID per object version, when versioning is on |

There are no directories. A "folder" in the console is a zero-byte object whose key ends with `/`. Renaming a "folder" really means **copying every object to a new key** and deleting the old ones.

### Consistency

Since late 2020 S3 offers **strong read-after-write consistency** for every operation. If a `PUT` succeeds, the next `GET` or `LIST` sees it. Old advice about "eventual consistency" and waiting before listing is out of date.

### Storage classes

You pay for storage, requests and retrieval. Different classes trade those against each other.

| Class | Good for | Watch out for |
|---|---|---|
| **Standard** | Active data | Highest storage price |
| **Intelligent-Tiering** | Unknown or changing access patterns | Small monitoring fee per object |
| **Standard-IA** | Infrequent access, rapid retrieval | **30-day minimum**, **128 KB minimum billable size**, retrieval fee |
| **One Zone-IA** | Re-creatable data | Stored in a **single AZ** |
| **Glacier Instant / Flexible / Deep Archive** | Archives | Minimum storage periods (90 to 180 days), retrieval delay or cost |

## Who Can Read This Bucket? 🔍

Access to an object is the result of **several layers**, and *all* must permit it.

| Layer | What it controls |
|---|---|
| **Block Public Access** | A master switch that overrides any policy or ACL that would make data public |
| **IAM identity policy** | What the caller's role may do (Post 02) |
| **Bucket policy** | A resource policy on the bucket: who may do what to it, with conditions |
| **VPC endpoint policy** | What may pass through a given gateway endpoint (Post 04) |
| **SCP** | Account-wide guardrails from AWS Organizations |
| **KMS key policy + IAM** | Whether the caller may use the key that encrypts the object (Post 05) |
| **ACLs** | A legacy mechanism. **Disabled by default on new buckets** and best left that way |

![The platform bucket and the S3-yes, KMS-no failure](content/aws/images/06-s3-access.svg)

### Encryption options

| Option | Key held by | Notes |
|---|---|---|
| **SSE-S3** | S3 | **Applied to every new object by default.** Free |
| **SSE-KMS** | KMS (you choose the key) | Audited in CloudTrail, key policy controls access, costs KMS requests |
| **DSSE-KMS** | KMS | Two layers of encryption for strict compliance needs |
| **SSE-C** | You send the key with every request | You manage it. Rarely worth it |

With SSE-KMS, every `GET` and `PUT` triggers a KMS call. At high request rates that adds cost and can hit KMS request limits. **S3 Bucket Keys** fix this by generating a short-lived bucket-level key from your KMS key, which cuts KMS calls dramatically. Turn them on.

## Nuances & Misconceptions 🧩

| What people assume | What's actually true |
|---|---|
| "S3 is a file system with folders." | It's a flat key-value store. **Prefixes are just text.** There's no rename, no append, and no real directory to lock. |
| "S3 is eventually consistent." | It's **strongly consistent** for all reads and lists. |
| "If the bucket is private, I'm done." | Private is the default. Dangerous settings come from **bucket policies with `Principal: "*"`**, public ACLs or a disabled Block Public Access. Turn Block Public Access on **at the account level too**. |
| "`s3:GetObject` in my policy lets me read the file." | Not if the object is encrypted with a KMS key you can't use. You also need `kms:Decrypt`, and nothing else (bucket policy, endpoint policy, SCP) can deny you. |
| "SSE-KMS costs the same as SSE-S3." | SSE-S3 is free. SSE-KMS adds **per-request KMS charges** and can be **throttled** by KMS limits on busy buckets. Enable **Bucket Keys**. |
| "Versioning protects me from deletes." | It does, but a `DELETE` just adds a **delete marker**, and every old version keeps costing you. You also need a **lifecycle rule** to expire noncurrent versions. |
| "Standard-IA is always cheaper." | It has a **30-day minimum** and a **128 KB minimum billable size**. For small or short-lived objects it's **more expensive** than Standard. |
| "I can delete a bucket in one click." | It must be **empty**, and with versioning that means **every version and delete marker**. Use a lifecycle rule or the console's *Empty* action. |
| "Bucket names are mine once I delete them." | Names are **global**. After deletion, someone else can claim yours, and old references may then point at *their* bucket. Include your **account ID** in names. |
| "A presigned URL is valid for as long as I set." | It's also limited by the **credentials that signed it**. Sign with a role session that expires in an hour and the URL dies in an hour. |
| "Unfinished multipart uploads are free." | Incomplete parts **are stored and billed** but don't show in normal listings. Add a rule to **abort incomplete uploads** after a few days. |
| "A bucket policy alone gives cross-account access." | Cross-account needs **both sides** to allow (Post 02), and the other account also needs KMS access if the data is SSE-KMS. |
| "S3 can handle unlimited requests." | Roughly **3,500 write and 5,500 read requests per second per prefix**. High-rate workloads spread across prefixes. |

## Lab: Build the Data Lake Bucket 🛠️

Sign in as Jim in **N. Virginia**. Use the CLI with `AWS_PROFILE=plat-admin`.

### 1. Turn on Block Public Access for the whole account

1. Open **S3**, then **Block Public Access settings for this account**, and choose **Edit**.
2. Tick **Block *all* public access** and save. Confirm.

This is a seatbelt that applies to every bucket, including ones someone creates by mistake next year.

### 2. Create the bucket

1. **Create bucket**. Type **General purpose**.
2. Name: `plat-data-<your-account-id>-us-east-1`. Region: **us-east-1**.
3. **Object Ownership:** **ACLs disabled (recommended)**.
4. **Block Public Access:** leave **all four** ticked.
5. **Bucket Versioning:** **Enable**.
6. **Tags:** `project = plat`.
7. **Default encryption:** **Server-side encryption with AWS Key Management Service keys (SSE-KMS)**. Choose **AWS KMS key**, then **Choose from your AWS KMS keys**, and select **`plat-data`**. **Bucket Key: Enable.**
8. Create the bucket.

Store the name in a shell variable for the commands below:

```bash
export BUCKET=plat-data-$(aws sts get-caller-identity --query Account --output text)-us-east-1
echo $BUCKET
```

### 3. Create the prefixes

Open the bucket and use **Create folder** three times: `raw`, `processed`, `models`. They'll appear as zero-byte `raw/`, `processed/` and `models/` objects.

### 4. Add a bucket policy that requires TLS

**Permissions, Bucket policy, Edit.** Paste the following, replacing `YOUR-BUCKET` with the bucket name:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyInsecureTransport",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": [
        "arn:aws:s3:::YOUR-BUCKET",
        "arn:aws:s3:::YOUR-BUCKET/*"
      ],
      "Condition": { "Bool": { "aws:SecureTransport": "false" } }
    }
  ]
}
```

Save it. A bucket policy that *denies* is safe to add: it narrows access and never exposes anything.

### 5. Create the lifecycle rules

**Management, Lifecycle rules, Create lifecycle rule.**

**Rule 1: `housekeeping`** (applies to all objects in the bucket)

- Tick **Delete expired object delete markers or incomplete multipart uploads** and **Permanently delete noncurrent versions of objects**.
- Noncurrent versions: delete after **30 days**.
- Incomplete multipart uploads: delete after **7 days**.

**Rule 2: `raw-to-ia`** (limit with the prefix `raw/`)

- Tick **Move current versions of objects between storage classes**.
- Transition to **Standard-IA** after **30 days**.

Acknowledge the warning about small objects, which the console shows because of the 128 KB minimum.

### 6. Generate and upload a dataset

Save this as `make_data.py`. It writes 5,000 synthetic customer-activity rows (plus a few duplicates and gaps, because real data has both):

```python
import csv
import math
import random

random.seed(42)
ROWS = 5000

with open("events.csv", "w", newline="") as f:
    w = csv.writer(f)
    w.writerow(["event_id", "user_id", "plan", "sessions_7d",
                "minutes_7d", "tickets_30d", "churned"])
    written = []
    for i in range(1, ROWS + 1):
        plan = random.choices(["free", "pro"], weights=[0.7, 0.3])[0]
        sessions = max(0, int(random.gauss(8 if plan == "pro" else 4, 3)))
        minutes = round(max(0.0, random.gauss(sessions * 14, 25)), 1)
        tickets = max(0, int(random.gauss(1, 1.2)))
        logit = 0.6 + 0.5 * tickets - 0.18 * sessions - (0.8 if plan == "pro" else 0)
        churned = 1 if random.random() < 1 / (1 + math.exp(-logit)) else 0
        # a few rows have no minutes recorded
        minutes_out = "" if random.random() < 0.03 else minutes
        row = [f"e{i:05d}", f"u{random.randint(1, 2000):04d}", plan,
               sessions, minutes_out, tickets, churned]
        w.writerow(row)
        written.append(row)
    # replayed events: exact duplicates of earlier rows
    for row in random.sample(written, 50):
        w.writerow(row)

print("wrote events.csv")
```

```bash
python3 make_data.py
wc -l events.csv
aws s3 cp events.csv s3://$BUCKET/raw/events.csv
```

```text
5051 events.csv
upload: ./events.csv to s3://plat-data-123456789012-us-east-1/raw/events.csv
```

That's 5,000 rows, 50 replays and one header: **5,051 lines**. We'll use every one of those problems in Post 19.

### 7. Confirm it was encrypted with our key

```bash
aws s3api head-object --bucket $BUCKET --key raw/events.csv \
  --query '[ServerSideEncryption,SSEKMSKeyId,BucketKeyEnabled]' --output json
```

```json
[
    "aws:kms",
    "arn:aws:kms:us-east-1:123456789012:key/1234abcd-12ab-34cd-56ef-1234567890ab",
    true
]
```

You never sent an encryption header. The **bucket default** applied the key.

### 8. See versioning and delete markers

```bash
aws s3 cp events.csv s3://$BUCKET/raw/events.csv      # upload again -> a second version
aws s3api list-object-versions --bucket $BUCKET --prefix raw/events.csv \
  --query 'Versions[].[VersionId,IsLatest]' --output table

aws s3 rm s3://$BUCKET/raw/events.csv                   # "delete"
aws s3 ls s3://$BUCKET/raw/                              # nothing listed
aws s3api list-object-versions --bucket $BUCKET --prefix raw/events.csv \
  --query 'DeleteMarkers[].[VersionId,IsLatest]' --output table
```

The object looks gone, but there are **two versions plus a delete marker**. Restore it by deleting the marker:

```bash
MARKER=$(aws s3api list-object-versions --bucket $BUCKET --prefix raw/events.csv \
  --query 'DeleteMarkers[0].VersionId' --output text)
aws s3api delete-object --bucket $BUCKET --key raw/events.csv --version-id $MARKER
aws s3 ls s3://$BUCKET/raw/
```

The file is back.

### 9. Reproduce "S3 allowed, KMS denied"

Open a **regular** CloudShell (not the VPC one) and assume the Post 02 role:

```bash
BUCKET=plat-data-$(aws sts get-caller-identity --query Account --output text)-us-east-1
ACCOUNT=$(aws sts get-caller-identity --query Account --output text)

read AK SK ST <<< $(aws sts assume-role \
  --role-arn arn:aws:iam::$ACCOUNT:role/plat-demo-reader \
  --role-session-name reader-test \
  --query 'Credentials.[AccessKeyId,SecretAccessKey,SessionToken]' --output text)
export AWS_ACCESS_KEY_ID=$AK AWS_SECRET_ACCESS_KEY=$SK AWS_SESSION_TOKEN=$ST

aws s3 ls s3://$BUCKET/raw/                   # works: S3 permission is fine
aws s3 cp s3://$BUCKET/raw/events.csv - | head -3
```

The first command lists the object. The second fails with an error along these lines (wording varies slightly):

```text
An error occurred (AccessDenied) when calling the GetObject operation: User:
arn:aws:sts::123456789012:assumed-role/plat-demo-reader/reader-test is not authorized to
perform: kms:Decrypt on the resource associated with this ciphertext because no
identity-based policy allows the kms:Decrypt action
```

The policy `plat-s3-read-demo` allows S3. Nothing allows **KMS**. This is the "S3 yes, KMS no" error, and now you know its shape.

### 10. Fix it, narrowly

Unset the temporary credentials (`unset AWS_ACCESS_KEY_ID AWS_SECRET_ACCESS_KEY AWS_SESSION_TOKEN`). In the console, open role **`plat-demo-reader`**, **Add permissions, Create inline policy, JSON**, and paste this (replace the key ARN with yours from step 7):

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "UsePlatKeyViaS3Only",
      "Effect": "Allow",
      "Action": ["kms:Decrypt"],
      "Resource": "arn:aws:kms:us-east-1:123456789012:key/1234abcd-12ab-34cd-56ef-1234567890ab",
      "Condition": {
        "StringEquals": { "kms:ViaService": "s3.us-east-1.amazonaws.com" }
      }
    }
  ]
}
```

Name it `use-plat-key`. Wait a few seconds, repeat the assume-role commands and the `aws s3 cp ... | head -3` line. You'll see the header and two rows. The `kms:ViaService` condition means the role can use the key **only when S3 asks on its behalf**, not by calling KMS directly. Unset the credentials again when you're done.

## Quick Quiz 🧠

**Q1.** A role can list an SSE-KMS bucket but gets `AccessDenied` on `GetObject`. Which two permissions do you check?

<details>
<summary>Show answer</summary>

`s3:GetObject` on the object ARN (bucket policy or identity policy) **and** `kms:Decrypt` on the bucket's key (key policy plus IAM). Listing needs neither the key nor object-level access, so it can succeed while reads fail.

</details>

**Q2.** You `aws s3 rm` an object in a versioned bucket. How do you get it back, and what's still costing you money?

<details>
<summary>Show answer</summary>

Delete the **delete marker** (by its version ID) and the previous version becomes current again. Meanwhile **every old version is still stored and billed**. Add a lifecycle rule to expire noncurrent versions.

</details>

**Q3.** Why does enabling a Bucket Key matter on a bucket that serves millions of requests?

<details>
<summary>Show answer</summary>

Without it, each request makes its own KMS call, which is billed per request and counts against KMS request quotas (it can throttle you). A Bucket Key lets S3 use a short-lived key derived from your KMS key for many objects, **cutting KMS requests dramatically**.

</details>

**Q4.** A 2 KB log file is moved to Standard-IA after 30 days. Why might your bill go up?

<details>
<summary>Show answer</summary>

Standard-IA bills a **minimum of 128 KB per object** and has a **30-day minimum storage duration**. A 2 KB object is charged as 128 KB, and retrieval adds a per-GB fee, so small objects cost more there than in Standard. (S3 lifecycle rules skip objects under 128 KB by default for this reason.)

</details>

**Q5.** Why is the `kms:ViaService` condition useful on the fix in step 10?

<details>
<summary>Show answer</summary>

It limits the key permission to calls that **S3 makes on the role's behalf**. The role can read objects but can't call KMS directly to decrypt arbitrary ciphertext, which keeps the permission as narrow as the actual need.

</details>
